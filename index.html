02 / FORENSICS

What it looked like, what it actually was

Anyone can list tools. The part of this job that is hard to fake is working out what is really wrong while a lending platform is down. Four real ones. Open any of them.

P0 · CORE LENDING CLUSTER

Aurora CPU pinned at 100 percent

Database saturated, queries queueing, and no obvious expensive statement in the slow log.
  • Performance Insights showed load climbing with no single expensive statement behind it.
  • Connection forensics showed sessions accumulating rather than cycling, far past what the workload justified.
  • Traced the growth to a HikariCP connection pool leak in a payment batch job that never returned borrowed connections.

OUTCOMECross-team remediation on the application side, a formal RCA, and preventive controls so a pool could not silently exhaust the cluster again.

RECOVERY · ZERO DATA LOSS

An Aurora cluster that would not open

A production cluster became inaccessible after a dependency it relied on was decommissioned.
  • Established that the cluster could not be recovered in place, so the question became how far back to go.
  • Ran point-in-time restore against a timestamp chosen to sit before the change and after the last consistent write.
  • Led failover and cluster restore with engineering leadership, verifying integrity before any traffic returned.

OUTCOMERecovered with zero data loss. The DR runbook covering PITR, Aurora restore and cross-account restoration came out of it.

LATENCY · PRODUCTION API

Threads frozen while the CPU sat idle

Response times collapsed while the host showed almost no load, and nothing useful in the application logs.
  • Idle CPU with stalled requests pointed away from capacity and towards blocking.
  • Took heap and thread dumps under load and analysed them rather than guessing from metrics.
  • Isolated a JVM deadlock, with threads contending on a shared monitor held inside an observability agent's instrumentation.

OUTCOMERoot cause sat in a third-party agent, not in our code. Found because the dumps were taken while it was happening rather than after a restart.

FLEET · DISK EXHAUSTION

A host filling up for no reason

Root volume at 100 percent on an application host. Clearing it bought a few days, then it came back.
  • Most of the volume sat in temporary directories left behind by a security scanning agent that never cleaned up after itself.
  • Rather than reclaim the space and move on, checked sibling hosts and found the same pattern on each.
  • Reclassified it from a one-host incident to a fleet-wide agent defect, alongside unrotated logs and unbounded retention.

OUTCOMEThe difference between an hour of disk cleanup and a problem that stops recurring is asking whether host two has it too.

05 / OPEN SOURCE

Built in public

The same thing I do at work, with the company specifics stripped out and the reasoning written down.

service-launcher

github.com/addsh/service-launcher →

One YAML file describes your services. A generator emits a parent stack holding one nested stack each, which clears CloudFormation's 500-resource ceiling and isolates a failure to the service that caused it. Every service shares the same two load balancers through host-based routing, so the marginal cost of one more service is only its compute.

The same architecture is implemented twice, once in CloudFormation and once in Terraform, with a written comparison of where each tool made the design easier or harder. Both paths are checked on every pull request.
